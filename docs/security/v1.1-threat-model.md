# SIDJUA V1.1 Security Threat Model — Data at Rest

**Status:** Accepted risk statement for V1.1 Beta
**Applies to:** SIDJUA V1.1.x container deployments (`sidjua/sidjua:1.1.x`)
**Decision:** Q5 answer from CEO sign-off, 2026-04-15
**Reviewed by:** CEO Goetz Kohlberg via Opus T1

---

## 1. Scope

This document covers data-at-rest security for the `/data` Docker volume introduced
in the V1.1.0 persistence fix. It does not cover data in transit (TLS), access
control (auth middleware), or agent governance (audit trail).

---

## 2. Data Stored on the `/data` Volume

After the V1.1.0 persistence fix, the following is stored on the `sidjua-data` named volume mounted at `/data`:

| Path | Contents | Sensitivity |
|------|----------|-------------|
| `/data/.system/sidjua.db` | All agent state, tasks, audit log, chat history, API tokens | High |
| `/data/config/config.json` | Admin password hash (bcrypt), session secret | High |
| `/data/config/mcp-servers.yaml` | MCP server endpoints, env var references | Medium |
| `/data/governance/` | Orchestrator config, governance snapshots | Medium |
| `/data/uploads/` | User-uploaded files (documents, images) | Variable |
| `/data/logs/` | Error log (PII-redacted by `pii-redactor.ts`) | Low |

---

## 3. Accepted Risks for V1.1 Beta

### R1 — Volume plaintext at rest

**Risk:** The `/data` volume is stored in plaintext on the Docker host filesystem.
A user with root access to the host (e.g., root on the Hetzner dev host) can read
all contents of the volume without authentication.

**Mitigation in V1.1:** None (host-hardening only — see Section 4).

**Acceptance rationale:** V1.1 is a beta release with no production customer data.
The deployment host is operator-controlled. The threat model accepts this risk for
the V1.1 timeframe.

### R2 — Admin password hash exposure

**Risk:** `config/config.json` contains the bcrypt hash of the admin password.
An attacker with volume access could attempt offline dictionary or brute-force
attacks against the hash.

**Mitigation:** bcrypt is used with a work factor that makes brute-force expensive.
The admin password is not stored in plaintext. Session secret is regeneratable.

**Acceptance rationale:** Same as R1. bcrypt hash is not plaintext-recoverable for
strong passwords.

### R3 — Session secret exposure

**Risk:** `config/config.json` contains the session secret used to sign session
cookies. An attacker with volume access could forge session cookies.

**Mitigation:** Per CEO Q4 decision, sessions are wiped on every container start.
A session secret leak is therefore only exploitable while the container is running.

**Acceptance rationale:** Acceptable for V1.1 beta scope.

## 4. Host-Hardening Recommendations (V1.1 Operator Guidance)

These are not enforced by the application but are strongly recommended:

1. **Restrict host access:** Only authorized operators should have root or Docker
   socket access on the deployment host.
2. **Docker socket security:** Do not expose the Docker socket to untrusted processes.
3. **Filesystem permissions:** Named volumes are stored under Docker's data directory
   (typically `/var/lib/docker/volumes/`). Restrict access to this directory.
4. **Backup encryption:** Use `sidjua backup create` for backups; consider encrypting
   backup archives before off-host transfer.
5. **Strong admin password:** Choose a strong admin password to resist offline hash
   attacks in case of volume compromise.

---

## 5. Out of Scope for V1.1 — Deferred to Post-V1.2

The following security controls are explicitly deferred. A follow-up
architecture ticket will be filed:

- **Volume encryption at rest** (LUKS, gocryptfs, or equivalent)
- **Secrets management** (Vault, SOPS, or equivalent for MCP credentials)
- **DSGVO Art. 32 compliance** (formal data processing agreement, encryption mandate)
- **Formal threat model** (STRIDE or PASTA methodology)
- **Enterprise security specification** (multi-tenant, audit trail, key rotation)
